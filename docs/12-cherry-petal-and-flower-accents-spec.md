## 1. Why

Two rendering contracts are written but unmet — the data is already plumbed
through core, only the consuming render path (and one sprite) is missing:

1. **Cherry `petal` tier collapses to `bloom`.** `unlockTier`
   ([web/render-garden.js:436-439](../web/render-garden.js)) already emits three
   cherry states from summed `recent_activity`:
   `petal` (≥ `CONFIG.cherry.petal` = 100 000) → `bloom` (≥ 15 000) → `bud`.
   `addSpringPetals` ([web/render-garden.js:557-559](../web/render-garden.js))
   already treats `petal` as the hotter state (12 vs 6 falling petals). But
   `addCourtyardObjects` only branches **bud vs not-bud** for the sprite
   ([web/render-garden.js:242](../web/render-garden.js)) and width
   ([:246](../web/render-garden.js)).
   **[v2]** Precisely: at the `petal` tier the *static sprite and width are
   identical to `bloom`* — only the falling-petal count differs. The peak tier is
   visually indistinguishable when motion is off / season ≠ spring. The
   `cherry_tree` manifest group ([assets/sprites/ivy_courtyard_manifest.json:1073-1084](../assets/sprites/ivy_courtyard_manifest.json))
   has only `cherry_tree_bud` (223×254) and `cherry_tree_bloom` (313×315).

2. **`flower_cluster` is shipped-but-orphaned.** Four sprites
   (`flower_cluster_01..04`, trimmed widths 141/137/183/192) exist on disk and are
   **[v2]** *grouped* into `groups.flower_cluster` by `groupSprites`
   ([web/render-helpers.js:1-7](../web/render-helpers.js)) — the manifest is
   fetched and grouped in [web/garden.js:29-33](../web/garden.js) — but **no render
   code ever places them** (zero references in `web/*.js`). Meanwhile
   [docs/sprite-rendering.md:30](./sprite-rendering.md) promises *"Recent activity
   controls fresh leaf overlays and flower probability"* and :44 *"Add flowers and
   small life only as accents."*

## 2. Deliverables

### A. New sprite asset — `cherry_tree_petal.png` (codex authors)

- Path: `assets/sprites/courtyard_style/cherry_tree_petal.png` (source of truth;
  `crates/tauri-app/build.rs:9-18` mirrors `assets/` → `web/assets/`).
- **Canvas 313×315 RGBA**, transparent background — identical footprint to
  `cherry_tree_bloom.png`, composites at the same `anchor:'bottom'` point with no
  re-layout.
- **Trunk + ground contact align pixel-wise with bloom** (same alpha baseline /
  bottom bbox), so bloom→petal does not make the tree jump.
- **Visually distinct from bloom at a glance**: fuller, denser, more saturated
  peak-sakura canopy, within the existing `courtyard_style` pink palette.
- **[v2] Agreed production method (codex + Pillow 12.2 / numpy 2.4, derive from
  bloom — NOT hand-drawn):**
  1. Load `cherry_tree_bloom.png`; keep the 313×315 canvas and the alpha channel's
     baseline untouched.
  2. **Canopy/blossom mask** = pixels where `alpha>0 && y<235 && r>=150 &&
     b>=115 && r>=g+8` (the pink/light-pink blossom region; the `y<235` and color
     gate protect the trunk and ground contact).
  3. On the mask: HSV **saturation ×1.18–1.25**, **value ×1.04–1.08**, slight warm
     hue shift.
  4. **Deterministic** (hash-seeded, no RNG) infill: sample a few center points
     from existing blossom pixels and stamp small 2×2 / 3×2 blossom clusters inside
     the canopy (≤1px neighborhood), colored from the local blossom palette mixed
     with a touch of light pink; **alpha never exceeds the local high-alpha** so the
     silhouette doesn't grow.
  5. **Never modify trunk pixels; never change the bottom bbox / ground contact.**
- Verify post-generation: 313×315 RGBA, alpha baseline row-for-row equal to bloom
  in the trunk/ground band, canopy visibly fuller+pinker.

### C. Render: 3-way cherry branch ([web/render-garden.js:238-251](../web/render-garden.js))

- **Sprite (:242):** map the tier explicitly with an **[v2] explicit fallback
  chain** (do not assume the manifest is complete — `addSprite` has no null guard):
  - `petal → cherry_tree_petal || cherry_tree_bloom || pickByToken(cherries,5)`
  - `bloom → cherry_tree_bloom || pickByToken(cherries,5)`
  - `bud   → cherry_tree_bud   || pickByToken(cherries,2)`
- **Width (:246):** 3-way — **[v2] `bud:78, bloom:100, petal:108`** (≤110 so the
  tree reads as peak without out-scaling the pavilion; "more" is carried mainly by
  the denser sprite + 12 falling petals).

### D. Render: activity-driven flower accents

Add `addFlowerAccents(groups, tiers)`, called from `renderEverything`
([web/render-garden.js:86-87](../web/render-garden.js)) right after
`addCourtyardObjects` so flowers cluster at the cherry base.

- **[v2] Count = discrete cherry tier:** `bud:0, bloom:2, petal:4`. (Max 4 = one
  pass over the 4 variants, no repeat. Coheres with "cherry + flowers peak
  together".) Uses `tiers.cherry` — no core change; `recent_activity` already
  summed in `unlockTier` ([:409](../web/render-garden.js)).
- **[v2] Season gating in JS** (single source of truth): early-return unless
  `sceneSeason()` ∈ {`spring`, `summer`} — flowers are a growing-season accent,
  hidden in autumn/winter. Mirrors how `addSpringPetals` is gated to spring via
  `addAmbientMotion`.
- **[v2] Placement near the cherry base only** (cherry is at x:23): `x ∈ [16,31]`,
  `y ∈ [91.5,94]`, **width 24–34**, **z ≈ 23**, `anchor:'bottom'`,
  `className:'flower'`. Do **not** spread across the whole ground band — that
  collides with bamboo (x≈3.5–12.5), stone_cat (x:34), lantern (x:60), cairn
  (x:68), path stones, pavilion.
- **Deterministic** layout via `jitter(i, seed)` ([web/render-helpers.js:39](../web/render-helpers.js)) —
  **no `Math.random`**. Vary variants with `pick(flowerGroup, i)`.

### E. CSS ([web/index.html:163-165](../web/index.html))

**[v2]** `.pg6-sprite.flower` currently has only a `filter`, so it inherits
`pointer-events:auto` (line 113) and `transform-origin:top center` (line 116).
Add:

```css
.pg6-sprite.flower {
  filter: saturate(0.82) brightness(0.92) contrast(0.96);
  pointer-events: none;          /* accents must never block vine / cat hover */

```

(No CSS `display:none` season rule needed — JS already skips off-season placement,
keeping one source of truth. Falling petals use a CSS hide because they're placed
unconditionally; flowers are not.)

## 3. Constraints / invariants

- **Privacy contract:** no network; no writes to source agent dirs. Sprite
  generation reads/writes only under `assets/sprites/`.
- **No core change.** Pure frontend + asset change.
- **[v2] Determinism (restated precisely):** for a *fixed* `(summary, settings,
  resolved season/time-of-day)`, the layout is a pure function with **no RNG / no
  `Math.random`**. (Output legitimately varies when those *inputs* change — season,
  time mode, motion, settings — that is by design, not nondeterminism.)
- **Graceful degradation.** Older caches / browser fallback lacking
  `recent_activity` must not error: flowers → count 0, cherry → bud/bloom via the
  fallback chain.
- **Modularity (CLAUDE.md §10):** all JS stays in `web/`; no presentation logic in
  core.

## 5. Verification

- **[v2] The committed sample already exercises the petal tier:**
  `web/data/garden-summary.json` sums `recent_activity` to **211,873 ≥ 100k**, so
  after implementation the browser preview shows the petal sprite + 4 flowers + 12
  falling petals (in spring) **with no data change**. This is the primary visual
  acceptance check.
- Petal tier: distinct sprite vs bloom; 4 flowers; width 108.
- Bloom tier (`15k ≤ ra < 100k`): bloom sprite, 2 flowers, 6 petals — otherwise
  **unchanged vs today** (regression guard).
- Bud tier (`< 15k`): bud sprite, 0 flowers (regression guard).
- `cherry_tree_petal.png` is 313×315 RGBA, trunk/baseline aligned with bloom.
- Manifest valid JSON; `cherry_tree` group has 3 entries.
- Flowers don't block hover on vines / cat / trinkets (pointer-events:none).
- Season toggle to autumn/winter removes flowers; back to spring/summer restores.
- **[v2] Sample is schema v2** (core `SUMMARY_SCHEMA_VERSION` = 4) and lacks
  `size_level` / `path_inferred` — it still drives this feature fine, but a
  schema-current sample/fixture refresh is tracked **separately** (the "doc/sample
  refresh" task), not in this spec.
- `cargo build` / `cargo tauri dev` runs `build.rs` to mirror the new PNG into
  `web/assets/`; pure browser preview needs `web/assets` synced (build once or copy).
